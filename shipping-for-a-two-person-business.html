Shipping for a two-person business: a bilingual Azure platform at $1.70 a month

A cleaning company ran on phone calls, text threads and a paper calendar. The replacement had to work one-handed, on a weak signal, in two languages, for a budget that could not carry a software bill.

October 2026 · 12 min read

Menifee Maids is a family-owned residential, commercial and post-construction cleaning company serving fifteen cities in Western Riverside County. The owner works on job sites most of the day, often with a weak phone signal, and a part-time helper assists. Before this engagement, requests came in by phone and text, availability lived on paper, and there was no reliable record of which jobs had been paid.

I designed, built, deployed and supported the platform that replaced all of that. It is live at menifeemaids.com. The engineering interest here is not any single service — it is what a hard constraint does to a design.

The constraints were the brief

Five problems came out of the first conversations. Lost and double-booked requests, because there was no single source of truth. A language gap, since much of the service area is Spanish-speaking while competitors' sites are English-only. Slow payment collection, with invoices sent by hand and no card payments. A phone-first reality, where any tool had to work between jobs on a poor connection. And a tight budget: a two-person business cannot carry a meaningful monthly software bill.

That last one is the constraint that shaped the architecture. "Near-zero fixed cost" is not a nice-to-have you bolt on at the end; it eliminates whole categories of design before you start.

Make running cost scale with usage rather than sit as a fixed bill, and the rest of the architecture follows.

Seven services, one front door

Customers and staff only ever talk to one thing: an Azure Static Web App and its built-in API. Data, files, email and payments sit behind it, and a separate Function App runs scheduled and background work.

The whole site and its thirteen-endpoint API deploy together on the Static Web Apps free tier, which also provides TLS, a custom domain, Microsoft sign-in and route-level role rules at no cost. Cosmos DB holds jobs, payments, availability, settings and customers on the free tier with capped throughput. Blob storage keeps job photos and archives, a storage queue backs up the booking path, and Azure Communication Services sends email from the client's own domain.

I kept Cosmos DB on manually provisioned throughput rather than autoscale, specifically because autoscale can climb past the free allowance. That is the kind of decision that only looks important on the invoice.

What the free tier costs you

Managed functions inside Static Web Apps are HTTP-only and have no managed identity. That has two consequences I had to design around: the website's API holds its keys in environment variables rather than using identity-based access, and anything on a timer or a queue trigger needs a separate Function App. So background work runs on its own Linux Consumption app, whose system-assigned identity holds the Cosmos DB and storage roles — no secrets on that app at all.

Offline-first, because the office is a job site

The staff dashboards are installable on a phone's home screen and expected to work on a bad connection. They read and write a local working copy; a sync engine pulls every 45 seconds and pushes about 1.5 seconds after a change, merging against a last-agreed snapshot.

Three-way merge is the part worth dwelling on. Comparing local, cloud and last-agreed lets conflicts resolve deterministically: a local edit pushes, a remote edit is taken, and when both changed the newest wins. A device never pushes before its first successful pull, so a stale copy can't overwrite newer data. And if more than three records vanish at once, the engine restores rather than deletes — a guard against a sync bug quietly emptying the business's job history.

The browser never decides the amount

The first payments design was a single static payment link. It cannot charge different customers different amounts, and its parameters can be edited by anyone who can read a URL.

What shipped instead creates a Stripe Checkout Session on the server, from the amount stored in the database, and reconciles through a signature-verified webhook. Prices cannot be changed by editing a link, payments mark themselves paid without manual entry, and card data stays with Stripe so PCI scope stays minimal. The live key is a restricted one with exactly two permissions: write Checkout Sessions, read Payment Intents.

The outage customers never saw

The hardest problem of the engagement was a production component that never started. The background Function App returned 503 on both the app and its deployment endpoint, the portal showed a runtime version of "Error", and the functions list would not load.

The investigation went layer by layer. Publishing from the workstation failed first on the wrong account and tenant, then on a missing worker runtime — both fixed, neither the cause. A package would upload but trigger syncing failed. A GitHub Actions workflow couldn't fetch app settings because the site was unavailable. Configuration review ruled out publishing restrictions and network access. An attempt to switch runtime from PowerShell silently did nothing, because the pipe character in the version string was read as a shell pipe. Rebuilding the app from scratch reproduced the identical fault, which proved it wasn't a corrupted app.

The root cause, confirmed with Microsoft Support: the app had been created on Node.js 24, which the Azure CLI recommended after refusing Node 20 as end-of-life. The Linux Consumption plan did not support Node.js 24, so no worker could start. Switching to Node 22 made the runtime healthy immediately. One follow-on fault remained — a deploy failing with 401 because the publish profile had gone stale — and replacing that secret produced a green deploy.

The reason this incident cost the business nothing is a decision made while it was still unresolved. The original design queued every booking for the Function App to write, so when that app couldn't start, bookings sat in the queue. I moved the customer path off it entirely: bookings now write directly from the API to Cosmos DB, and the queue is used only when that write fails. The fallback writer is create-only, so a delayed copy can never overwrite an edit staff have made since.

Anything customers depend on shouldn't hinge on a background component.

Customers kept booking throughout. The visible consequence was that reminders and archiving didn't run — which mattered, because archiving is what preserves records before an automatic ninety-day deletion removes them. That raised the priority considerably.

Testing against the real code

Every release was tested before the client saw it, and not against mocks of my own API. A local harness runs the actual Azure Functions handlers behind a small HTTP server, with in-memory stand-ins for the database, storage, the queue, email and Stripe, and it simulates the platform's sign-in so tests can act as an owner, a helper or an anonymous customer. A headless browser then drives the real pages at desktop and phone sizes, with simulated clocks and time zones where it matters.

That adds up to more than 130 automated checks across eleven suites, rerun on every release from v4 through v14: cross-device sync, notifications in both languages, live-mode payments with tampered links and forged webhooks rejected, photo attachments and HMAC-protected links, QR hand-off decoded to confirm the exact number and message, and a layout sweep of thirteen pages at seven widths.

One habit from that work is worth naming. When a check failed because of the test itself — a case-sensitive match against a capitalized label, a size threshold too strict for synthetic images — I fixed the test and said so, rather than weakening the product to make the suite green.

Smaller bugs, same loop

A dozen smaller issues followed one pattern: reproduce, hypothesize, change one variable, fix the cause rather than the symptom, then add a check so it can't return silently. A few earned their place in the report:

  • Bookings never reached the database. The page and dashboard shared one browser's storage, so a "successful" booking existed only on that device. Fixed by server-side writes and the sync engine
  • Past time slots were offered. The code checked the date but not the time of day, and used the visitor's time zone. Fixed with Pacific-time filtering, a one-hour lead and enforcement in the API as well as the page
  • Photos went missing from texts and emails. Browsers can't attach files to another app, so the platform sends the email itself with attachments, and texts carry a private link whose key is an HMAC of the job number
  • Customers were emailed before review. The client wanted control of the wording, so every message is now pre-written in the customer's language and shown for approval; nothing sends until someone presses Send

That last one cost a tap per message and was accepted deliberately. It is a reminder that the right answer sometimes makes the software slightly less automatic.

What it costs

The projected running cost is about $1.70 a month at roughly 200 jobs: Static Web Apps, Cosmos DB and Functions at zero on free tiers, around fifteen cents of blob storage, a cent of queue, about thirty cents of email, and an amortized domain. Adding a company texting number would take it to about $10.50, plus a one-time carrier registration fee. A budget alert guards against surprises.

The client also got an exit path that doesn't depend on me. Each release is a versioned package with a file list, a cache-version bump and a PowerShell script that refuses to run against a repository with uncommitted changes, copies the files, stops on untracked files, then commits and pushes. GitHub Actions deploys, and the client confirms the green check and runs the post-release checks.

What I'd carry forward

Check the support matrix, not just the tool's advice — one unsupported runtime version stopped every background job. Keep the critical path short. Verify where data lands rather than what the screen says, because a local-only dashboard looked like it worked. Test assumptions about external systems; one test email exposed a closed mailbox. And document as you go: the screenshot log made the support case, the client runbooks and the report itself possible.

Two items stay open and belong in the open, not in a footnote: keys and the deployment credential that were visible during setup need rotating, and the sample testimonials on the site need replacing with genuine reviews before anyone promotes them.
